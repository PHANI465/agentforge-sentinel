## R62 cross-process correction (89c34ea; DEMO01 da0fc08, 79ade16)

- **Fix** (`documents._recover_bridges`): two kinds of bridge record are left untouched and
  never signalled, but now **count as kept**, so `recover()` keeps recovery pending and
  analysis is refused (`503 document_worker_recovery_pending`):
  - a record of this process's own in-flight call;
  - a record owned by another API process that is verifiably alive, or whose state is
    unknown.

  Before, both were skipped uncounted, and `recover()` could report
  `{kept: 0, pending: false}` with a recorded bridge alive. They clear only by verified
  absence, verified pid reuse, or an identity-checked stop once the owner is gone. The
  unknown-state, durable-record, failed write/rename and reused-pid behaviour is
  unchanged.
- **Tests** (`tests/test_doc01b_r62_cross_process.py`; helper
  `tests/support/doc01_second_api.py`):
  - **Live owner:** real test-owned "owner API" and "bridge" sleepers with genuine
    creation identities and a `stop_unconfirmed` record in the shared store. A **separate
    interpreter process** (the second API, with its own service, document service and
    app) reports `recover == {kept: 1, pending: True}` and refuses analysis. Both processes
    are untouched (same identities) and the record stays. After the owner really exits,
    another separate API process verifies the orphan bridge, stops it, clears the record
    and analyses (200).
  - **Own in-flight call (control):** kept and unsignalled while in flight. After it
    leaves the in-flight set and its bridge is verified gone, `recover() == {kept: 0,
    pending: False}` and the store is clean.
  - **Unknown owner state:** kept, no signal, both processes alive.
- **Failing-first** (`.agent/doc01-b4/failing-first/`, the new tests against exact
  a3d1a6c): Windows and native each 3 failed. The separate API returned `{kept: 0,

  - The first Windows attempt (`windows-run1-child-clock.log`) also exposed a test-harness

- **Effect:** a recovery pass that runs while a call of this or another live API process is

## R62 follow-up (097eb77, test fix 50137c8; DEMO01 02ca0f1, 1b6ac30)

- **Four-state process lookup** (`documents.process_state`): `gone`, `live` with its
  creation identity (a different identity means the pid was reused) or `unknown`.
  - **Windows:** only `ERROR_INVALID_PARAMETER` from `OpenProcess` is absence. Access
    denied, any other error, or failing `GetExitCodeProcess` / `GetProcessTimes` is unknown.
  - **Linux:** `ENOENT` / `ESRCH` is absence; a zombie counts as exited. Permission or I/O
    errors and malformed stat are unknown.
  - **No `/proc`** (for example macOS) is unknown.
  - Only absence or a confirmed different identity clears a record. Unknown is never
    signalled.
- **Durable evidence before uncertainty:**
  - Every bridge call writes a launch intent, `api-bridge/bridge-<nonce>.json` (no pid),
    before starting the process, and its pid and creation identity right after.
  - Each write is retried once under a fresh temporary name. A pid-bearing temporary
    whose replace fails is kept as evidence.
  - If the launch intent cannot be written, nothing is launched: `503 unavailable`.
  - If no complete pid record can be written, the bridge is stopped before the request
    returns. If that stop cannot be confirmed, the launch intent and pid temporary stay
    and recovery is pending.
  - A timeout with an unconfirmed stop keeps the record (`stop_unconfirmed`). Completed or
    confirmed-stopped calls remove their records.
- **Recovery** (`_recover_bridges`) groups records **and** temporaries per call and skips
  this process's running calls, plus calls of another API process verified alive. Every
  recorded pid must then be confirmed gone or reused; a still-verified bridge is stopped
  and its exit confirmed. Unknown state, unreadable files, or a launch intent with no pid
  evidence keep the group: analysis stays refused, nothing is signalled, and an operator
  can remove it after checking.
- **Tests** (`tests/test_doc01b_r62_followup.py`, 16 cases; 9 run on Windows, 13 natively):
  - **Unknown lookup:** a real test-owned sleeper with its genuine identity under an
    injected unreadable lookup. The current and a fresh API instance both stay blocked,
    with no signal, and the sleeper stays alive. With the lookup working again, recovery
    stops exactly that process.
  - No-`/proc` (macOS-style) case, and Linux and Windows classification of each fault.
  - Live identity and the reused-pid case.
  - **Durable evidence:** persistent write failure and persistent replace failure of the
    pid record, with a real hung bridge whose kill was refused. After restart there is
    never a success while it lives; the replace case recovers through the kept
    temporary.
  - Transient write failure, retried and recovered after restart.
  - Confirmed-absence control.
  - No token, store path or injected path text in any error or record.
  - The existing kill-failure, unconfirmed-exit, reused-pid and unreadable-record tests
    pass unchanged.
  - The test-side liveness check was changed in 50137c8 to use process state, because
    `kill(pid, 0)` counts a not-yet-reaped zombie as alive.
- **Failing-first** (`.agent/doc01-b3/failing-first/`, the new tests against exact
  aca58f2): Windows 8 failed, 1 passed, 7 POSIX skips; native 12 failed, 1 passed,

## Review corrections R60-R63 (cfa94ab; DEMO01 f3234fe, 70991f1)

- **R60, upload cap** (`api.read_limited`): the prospective size is checked before a chunk
  is appended. One 32 MiB chunk is refused with a measured peak allocation under 4 MiB
  (tracemalloc). Declared-oversize refusal unread, error codes and order are unchanged.
- **R61, exact counts** (`http_v13`):
  - `project_analysis` requires `records_page.{offset, limit, total, records, next_offset}`
    and `unparsed_total`; it no longer defaults any of them. An analysis page must start
    at offset 0.
  - New `DocumentAnalysis` / `RecordPage` validators enforce:
    - returned records ≤ limit, and offset + returned ≤ total;
    - `next_offset` equals offset + returned exactly when records remain, otherwise null;
    - `unparsed_total` ≥ the unparsed items returned;
    - `coverage.records_typed` and `rows_unparsed` agree with the totals.
  - Malformed or contradictory bridge answers give `502 document_worker_failed`.
  - Validators do not change the JSON schema, and the OpenAPI and all v1.3 examples are
    byte-identical; the export check passes. Genuine zero, partial, unsupported and error
    answers (all 14 recorded) still project.
- **R62, uncertain bridge stop** (`documents`):
  - The bridge's creation identity is captured at launch: Windows `GetProcessTimes`, Linux
    `/proc` start time.
  - A failed kill, or an exit that cannot be confirmed, writes
    `<store>/api-bridge/bridge-<pid>.json` with the pid and identity only, sets recovery
    pending and returns the fixed `504 document_worker_timeout`. No raw exception or
    process text escapes.
  - Recovery runs before the next analysis, including after an API restart. It stops the
    process only while its identity still matches, and confirms the exit.
  - A reused pid is never signalled; its record is cleared.
  - An unreadable record, or a live process without a recorded identity, keeps analysis
    refused.
  - **Owned real-process proof:** a really hung fake-bridge process whose kill was refused
    stayed alive and was recorded. The next request in the same process was refused, and
    the parser did not run again. After a restart, recovery stopped that exact process
    (the inner interpreter is confirmed dead) and analysis proceeded.
- **R63, worker identity:**
  - The first `status` answer registers the digest, which must equal the pin when one is
    set.
  - Every later request sends `expect_source_sha256`. The real bridge refuses with
    `identity_mismatch` before any operation if its own digest differs, and every answer
    now carries `worker_protocol` and `worker_source_sha256`. The API rejects answers that
    lack the identity or carry another one, and requires each analysis's `parser` digest
    to match.
  - A mismatch gives `503 document_worker_identity_changed` with no report. When it shows
    up in an analysis result, parsing may have run, so recovery is also required before
    reuse.
  - Restarting with a pin and a changed worker gives `503 document_worker_unavailable`.
    Without a pin, a restart registers the worker then on disk (documented).

## Implemented

1. **Pre-API worker correction** (`f9fce13`, `39f6df4`): the Windows `_write_record` /
   `os.replace` sharing conflict.
   - **Reproduced first:** 6 failing tests at 0dd848e. With a real open reader handle,
     cleanup raised `WinError 32` out of `extract`, which crashed the supervising process.
     A failed replace left an orphan `r_*.tmp`. A pid stored only in a `.tmp` was
     "recovered" without being stopped.
   - **Fix:** unique temporary names and a 2 s retry for transient `PermissionError`.
   - A record write failure is now `error` with `recovery_record_write_failed:<state>`,
     never a success.
   - A temporary is kept only when it carries a pid, and cleanup never raises.
   - Recovery treats temporaries as evidence. It reports `temporary_record_unreadable_kept`
     and `orphan_temporary_removed`.
   - This supports, but does not prove, the explanation for the historical intermittent
     crash-test failure.
2. **Worker bridge** (`31382f2`, `8b642d6`): `docworker.bridge`, protocol
   `sentinel.doc01.bridge/0.1`, handling one stdio request per process. Its operations are
   `status`, `ingest`, `analyze`, `records`, `delete` and `recover`.
   - The size and framing of the bytes are checked, then the content (PDF / ZIP / UTF-8
     text, OLE refused) before a handle is issued.
   - The full result is persisted beside the handle under the same owner.
   - It returns a compact view: records are paged (at most 500 and 2 MiB); page and
     narrative text are dropped; duplicate-group evidence lists are capped with totals.
3. **Contract freeze before any route** (`7ec6d24`):
   - decision 0010 (DOC01 owns v1.3, and AN01's provisional label moves to v1.4 or later);
   - the API document;
   - the `http_v13` DTOs and a projection of the worker result onto them;
   - real bridge answers recorded for 14 fixtures;
   - 31 `examples-v1.3` files built only from DTOs and recorded answers.
4. **API** (`1754128`):
   - **Routes:** `POST /v1/documents?format=` (raw bytes; octet-stream or format media
     type; streamed 10 MiB cap; no multipart, no filename), `POST …/{handle}/analysis`,
     `GET …/{handle}/records` and `DELETE …/{handle}`.
   - **Authority:** the opt-in `analyze_document` capability, also available as
     `sentinel create-session --with-document-analysis`. The four default grants are
     unchanged. A session without it gets 403; a missing, foreign, tampered, malformed or
     expired handle gets an identical 404.
   - **`sentinel.documents`:**
     - starts the registered interpreter (`SENTINEL_DOC_WORKER_PYTHON`, `SENTINEL_DOC_STORE`,
       optional source pin) with a minimal environment, cwd set to the store, stdout capped
       at 8 MiB and wall-clock bounds;
     - derives a per-session owner key, so the token never reaches the worker;
     - runs one analysis at a time;
     - marks *recovery pending* after a timeout, crash, invalid answer or unconfirmed stop,
       and refuses analyses with 503 until a recovery pass keeps nothing;
     - otherwise fails closed: 503, 502 or 504 respectively.
   - **Versions:** v1.2 is frozen by SHA-256 (`b52f8fd4…`); v1.3 is active (`d4306c65…`).
5. **Real-process check** (`4f59b57`, `26897f5`, `cd8f0f4`): `scripts/doc01_api_e2e.py` runs
   a disposable Postgres cluster, a real `uvicorn` API and the real locked worker.
6. **DEMO01 capture refresh** (`a9808ce`, `5d0f0da`, `bbc2bb6`); see "Coordination".

## Not verified / gaps

- **Fake bridge in the app gate.** The app gate uses the fake bridge; the real worker is
  exercised only by `doc01_api_e2e.py` (run explicitly). The real-worker timeout and
  POSIX-orphan recovery path through the API is exercised only with the fake (`hang`), not
  with a real hung parser.
- **Per-process state.** Busy and recovery-pending state is per API process. Two API
  processes sharing one store are not coordinated.
- **No quotas.** There is no per-session upload or handle quota; disk use is bounded only
  by the 10 MiB cap and the one-hour lease. Expired handles are purged only during
  recovery passes, not periodically.
- **Weak Windows process check.** The Windows "no worker processes left" e2e check reads
  `tasklist` window titles; the empty run, record and recovery directories are the
  stronger proof. The native check uses `pgrep`.
- **Not claimed:** UI, hosting, private files, OS isolation, OCR, PDF tables, LLM
  narrative, measured throughput.
- **Final checks:** the exact final-commit gates are reported in chat.
