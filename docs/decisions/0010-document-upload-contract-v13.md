# 0010: Local document upload and feedback contract (HTTP v1.3, DOC01 Part B)

- Status: proposed (candidate for Codex review; not accepted)
- Date: 2026-11-12
- Decided by: pending Codex review; proposed by Claude Code under
  `docs/prompts/CLAUDE_DOC01_PART_B_BACKEND.md`

## Context

DOC01 Part A (accepted at `8f7bd87`, merged in `662572e`) provides a separately locked local
worker. It extracts typed, evidence-located feedback from text-layer PDF, UTF-8 CSV and XLSX
files inside a bounded child process. Part B exposes that worker to the analyst API.

The active public contract is v1.2. AN01 earlier used *v1.3* as a provisional label for its
reports API, but nothing was frozen under it, and no reports API is assigned.

## Decision

1. **Contract order.** DOC01 owns v1.3. AN01's provisional label moves to v1.4 or later,
   when its reports API is actually assigned. When v1.3 becomes active:
   - `openapi.v1.2.json` is frozen by SHA-256, as v1 and v1.1 already are;
   - the v1, v1.1 and v1.2 example sets are still regenerated byte-identically.
2. **Additive only.** v1.3 adds four document routes and one opt-in capability string.
   - Every v1.2 path, operation and component schema stays byte-identical. The single
     exception is the `SessionView.capabilities` item enum, which gains `analyze_document`.
   - The accepted p1 model, case, approval and action shapes, and the default analyst
     grants, are unchanged.
   - The UI already ignores capability strings it does not know.
3. **Opt-in authority.** `analyze_document` is never in the default grant of four. A session
   without it gets `403 permission_denied` on every document route. A missing, expired,
   malformed or foreign handle gives one indistinguishable `404 not_found`.
4. **Raw binary upload, no multipart.**
   - The request is `POST /v1/documents?format=csv|xlsx|pdf`. The body is the file's bytes,
     and the content type is `application/octet-stream` or the format's own media type.
   - No multipart dependency is added. No filename is read, and no path is derived from a
     filename, handle, URL or document text.
   - The body is capped at 10 MiB while it is streamed: a declared oversize body is refused
     unread, and an understated one stops at the cap.
   - The worker re-checks the content (PDF signature, OOXML ZIP, UTF-8 text without NUL)
     before it issues a handle.
5. **A registered worker, never imported.**
   - The API launches the operator-configured worker interpreter as one process per
     request, through the bridge protocol `sentinel.doc01.bridge/0.1`. Its environment is
     minimal, and the session owner key is passed in an environment variable.
   - The interpreter (`SENTINEL_DOC_WORKER_PYTHON`) and the marker-owned store
     (`SENTINEL_DOC_STORE`) come only from the server's environment. An optional pin,
     `SENTINEL_DOC_WORKER_SHA256`, must match the worker's reported source digest.
   - No worker dependency is imported into the app, and the app lockfile is unchanged.
   - If the configuration is absent or wrong, the routes fail closed with `503`.
6. **Bounded result transport.** The worker can emit about 12 MiB at its 20,000-row cap.
   The analysis response therefore carries:
   - the first page of records (at most 500, default 100, and at most 2 MiB);
   - every count with its denominator;
   - capped evidence lists with their totals.

   Page text and narrative text are not returned. Further records come from
   `GET .../records?offset&limit`, served from the result persisted beside the handle under
   the same owner, so the parser is not run again.
7. **Separate from casework.** Upload and analysis write no transaction, case, approval,
   audit or simulated-action row.
   - No document text is interpreted as an instruction. No model receives the file.
   - Findings are data-quality observations. A fixed `interpretation` string says the
     result is not a fraud verdict, authenticity check or calibrated score.
8. **Session owner key.** Each request derives
   `sha256("sentinel.doc01.owner.v1" ‖ tenant ‖ session ‖ token)`.
   - The bearer token itself never leaves the API process.
   - The store keeps only the hash of the owner key.
   - Handles survive an API restart for their own session, until their one-hour lease
     ends.
9. **Lifecycle bounds.**
   - One analysis runs at a time per API process; a concurrent one gets
     `503 document_worker_busy`.
   - Every bridge call has a wall-clock bound.
   - A bridge timeout, crash or invalid answer, or a result whose stop was unconfirmed,
     marks the worker *recovery pending*. Further analyses are refused
     (`503 document_worker_recovery_pending`) until a recovery pass keeps nothing.
10. **Pre-API worker correction.** Before this route existed, the Part A Windows
    `_write_record` / `os.replace` sharing conflict was reproduced and fixed. It now
    retries, never leaves an orphan temporary record, and never reports an unrecorded run
    as a success; recovery reads temporaries as evidence. See the worker protocol,
    "Record writes".

## Compatibility effect

- **v1.2 clients:** every response they consume is byte-for-byte unchanged, unless a session
  was explicitly created with the new opt-in. That session's `SessionView` then lists
  `analyze_document`, which the current UI ignores.
- **v1.3 additions:** `/v1/documents`, `/v1/documents/{handle_id}`,
  `/v1/documents/{handle_id}/analysis`, `/v1/documents/{handle_id}/records`, plus status
  codes 413, 415, 502, 503 and 504 for those routes only.
- **Frozen artifacts:** v1, v1.1 and v1.2 snapshots and examples, `contracts/v1`,
  `contracts/agents` and the p1 model registry are untouched.

## Consequences

- The v1.3 DTOs and example bodies (`contracts/http/examples-v1.3`) were frozen in a commit
  before the routes were implemented. The route commit must reproduce them
  byte-identically through real HTTP calls.
- The worker answers used for the examples are recorded from the real bridge
  (`tests/fixtures/doc01/bridge_recorded.json`). The app gate replays them through a fake
  bridge process, so the gate needs no worker environment. A separate real-process run
  (`scripts/doc01_api_e2e.py`) exercises the production API, the real worker and a
  disposable Postgres.
- Not claimed: hosted or multi-user use, private customer files, OS-level network or
  filesystem isolation (see the worker protocol), OCR, PDF table typing, an LLM narrative,
  or measured throughput.
