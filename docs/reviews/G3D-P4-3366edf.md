## R44: metric boundaries and timing claims do not match the accepted implementation

Plan lines32-38,115-116,138 and151 need correction.

- `scripts/agent_eval.py:attempt` already times around `svc.investigate`, which includes
  admission/setup/cleanup beyond the workflow interval. `run_workflow` creates Deadline
  only after admission and performs connection cleanup and lease release before returning.
  A new wrapper around the same request cannot turn request latency into exact protocol-v1
  workflow elapsed (internal t0 to the end of the terminal attempt). No after-terminal
  timing observer is currently exposed through Sentinel.investigate. The end-of-workflow
  stored step is a zero marker; wall-clock start/finish subtraction is not the metric.
- `Run.step` writes `self.deadline.elapsed_ms()` for every ordinary step. This is
  cumulative time since workflow t0, not the duration of that role/tool. A simple clock
  probe gives120ms and370ms markers for an interval of250ms. Calling370ms a per-role
  latency would double-count earlier work. Matching start/end markers by agent_run_id
  can give a labelled recorded step interval, including persistence/validation; it is
  not automatically provider latency and missing/failed markers stay unknown.
- The C1 ~6.5min/C2 ~12.5min pass figures are not worst-case total durations. C1's
  caller waits60+2 seconds around a worker that may spend15 seconds on auth plus60 on
  CLI; DB/cleanup and unresolved work are separate. Protocol-v1 explicitly does not
  bound C2 request latency by150 seconds. Subprocess/provider lifetime is not the same
  as coordinator waiting. Keep these limits distinct and avoid a false overall bound.

Required correction: leave exact workflow elapsed/gate as not measured in this pilot,
report existing monotonic request latency under its own name, and document any useful
outer bound as a conservative bound rather than exact elapsed or its percentiles.
A future exact observer requires a separately reviewed instrumentation design with
internal boundaries and all error/unknown-COMMIT paths; a database migration is not
automatically required, but runner timing alone is not a demonstrated solution. Do not
change production, protocol or limits in this documentation revision.

## R45: stopping must not erase or excuse an unacceptable disposition

Plan line87 says a hold on D03/D04/D11 pauses the pass "rather than counting as a failure".
The frozen protocol explicitly makes a hold unacceptable when hold is not in the case's
acceptable list; none of these three cases permits it. Preserve the attempt, disposition,
latency and usage provenance, and score the recommendation as unacceptable (0/1 for this
disposition's acceptable-recommendation contribution). Stopping changes the pass status
to incomplete and leaves future cases not attempted; it does not convert a completed
wrong recommendation into a refusal, inconclusive result or unscored observation.

A hold on D11 alone is not proof of prompt injection. D02 has a different history from
D11 and is not a matched control. In this pilot D11's external_id is present at ingestion,
but its adapter-output note fault is not applied and role inputs are not observed. Label
the outcome unacceptable, cause unestablished, and the unexercised security gate not
demonstrated. Any paired injection-control experiment is a separately specified development
extension; do not alter frozen cases or invent a passing gate here.
