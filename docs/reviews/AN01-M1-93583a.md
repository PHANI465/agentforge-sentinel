## R53 — P1: recovery can remove an active controller's lock

Source: scripts/benchmark_reports.py:1334 (`recover_command`), with lock acquisition at
Run.acquire_lock and the stage's pre-launch interval.

There is no controller-identity/ownership check before recovery. During the real interval
after acquire_lock and before a worker is recorded, state.worker is null. My probe uses
the live probe process PID as the lock holder: recover returns 0, removes the lock and
reports nothing kept while that owner remains alive. No process signal was needed. With
a worker recorded, recovery can also try to terminate it without establishing that its
controller has stopped. Another stage can then enter or collide with an active controller.

Record controller identity and an invocation/ownership token before mutable stage work.
Serialize recovery against admission. Refuse recovery of a verified live controller;
unknown/missing/stale identity must not authorize a kill or blind lock deletion. Permit
recovery only after the controller is proven absent and any worker/cluster ownership is
verified. Release only the lock owned by that invocation. Cover the pre-launch gap and a
live-worker interval through actual public entry points with intercepted negative signals.

## R55 — P1: the statement is submitted with an exhausted budget

Sources: scripts/report_benchmark_support.py:1013–1029 and :826 (`bounded_call`).

Budget is checked before Ka (set_config), then the report SQL thread is launched without
a fresh minimum/expiration check. Controlled report-clock probes use B=400,R=250:
after Ka takes 90 ms, only 60 ms remain, yet SQL is submitted and the outcome is ok; after
Ka takes 160 ms, work is already 10 ms expired and SQL is still submitted with wait=0,
again observed as ok. A 10 ms arming control leaves 140 ms and correctly permits work.

Recheck remaining budget and valid server timeout immediately before report SQL submission;
if the operation no longer fits, send no report SQL. bounded_call itself must refuse a
non-positive wait before launching a thread. Boundaries must not turn into zero/no-limit
server timeouts. A late worker reply cannot retroactively qualify an on-time result:
classify against the configured monotonic deadline and recorded arrival, even when the
waiting thread wakes late. Add deterministic post-arm and delayed-notice/late-arrival
tests and feasible real-database controls without widening existing assertions/timeouts.

## R56 — P1: reservation/connection ownership is lost on error paths

Sources: scripts/report_benchmark_support.py:816 (`_do_close`) and :1006 (on_connect).

A synthetic connection whose close raises and leaves it open is counted as closed: its
reservation is released, quarantine is empty and outcome is ok. Capacity therefore no
longer bounds the actual retained resources. A real acquired connection followed by an
observer hook error is also outside the try/finally: the probe sees zero close calls,
one reservation stranded and no quarantine/recovery owner.

Establish ownership immediately after acquisition and cover hook/setup failures. Release
a resource reservation only after confirmed final close or definitive acquisition failure
with no connection. A close failure must retain a named owner/reservation and a safe
failure/recovery state; a logical closed flag is not proof of actual close. Keep failure,
retry/finalization and coordinator-release accounting distinct. Never double-release or
touch workflow quarantine. Demonstrate close failure and hook failure, not only healthy
close and artificially delayed successful close. Preserve Ctrl-C/SystemExit semantics
while ensuring finally transfers or closes every acquired resource.

## R57 — P2: report results and read provenance contradict the design

Source: scripts/report_benchmark_support.py:1085 (`run_report`), :509 (`shape`) and :1020.

An answered read set with unanswered ROLLBACK is correctly labelled prototype200, but
run_report drops its body because kind is rollback_unanswered rather than ok. The
reviewed §5.3 explicitly permits200 **with the report**, since all reads answered.
The independent probe supplies a valid answered result set and receives body=None.

Separately, the runtime captures actual read_at before the first armed statement, but
the DTO and workload query use request.read_at from before acquisition. With an explicit
October3 cutoff and a runtime read boundary October4, the DTO incorrectly advertises
October3 as read_at. This matters when acquisition waits outside B; one timestamp cannot
silently stand for both the chosen cutoff and actual read boundary.

Use one authoritative snapshot-bound read_at consistently in SQL parameters and DTO
provenance, preserving an explicit as_of and handling default cutoffs/cursor bindings
according to the design. Keep a fully answered report when only readonly rollback is
unconfirmed, with its resource still safely retired. Failed/incomplete reads must never
fabricate a body. Add actual run-path tests, not only mocked shape assertions.
