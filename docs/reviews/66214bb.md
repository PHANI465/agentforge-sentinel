## R12 follow-up [P2]: distinguish stopped from unknown database status

Locations: [browser_stack.py:329](E:/PHANI/sentinel-wt/claude-browser-fixtures/tests/support/browser_stack.py:329), [_cluster_running:379](E:/PHANI/sentinel-wt/claude-browser-fixtures/tests/support/browser_stack.py:379).

_cluster_running maps every nonzero pg_ctl status result to false. stop consequently treats a failed status command as proof the database is stopped. An intercepted process-free probe made cluster.stop raise CalledProcessError and status return 1; stop returned ok:true, database_stopped:true and state_removed:true while also reporting database: pg_ctl stop failed. No live database status failure was induced.

PostgreSQL 14 distinguishes status 3 (not running) from 4 (accessible data directory not specified); other command failures are not affirmative proof of shutdown. See the primary [pg_ctl documentation](https://www.postgresql.org/docs/14/app-pg-ctl.html). Correction: represent running/stopped/unknown explicitly. Preserve recovery state and return failure for errors/unknown status; do not delete database files or claim database_stopped:true from an unsuccessful probe. Handle pre-initialization cleanup as its own explicitly verified state rather than treating every status error as stopped.

Acceptance: intercepted status results for running, known stopped, inaccessible/unknown and execution failures; unknown outcomes leave state intact and do not report success. Keep real successful stop/retry tests.
