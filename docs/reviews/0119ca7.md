## R18 [P1]: an existing role is not made or verified least-privileged

Location: [roles.py:52](E:/PHANI/sentinel-wt/claude-backend-reliability/src/sentinel/db/roles.py:52), through the grants at line 74.

NOSUPERUSER/NOCREATEROLE/NOBYPASSRLS/NOINHERIT and the other restricted attributes apply only in the CREATE ROLE branch. An existing role skips that branch; its ownership, memberships, elevated attributes and direct schema grants are not validated. Revoking table grants and revoking CREATE from PUBLIC do not remove those other sources of authority.

Independent probes on fresh owned disposable clusters confirmed both variants:
- a pre-created privileged role remained superuser after grant_runtime and could disable audit triggers (re-enabled before teardown);
- an ordinary NOSUPERUSER role with a prior direct CREATE grant on public retained that grant and created a table after refresh.

No existing user/system role or outside database was altered. Probe clusters were stopped and removed. Reproducer: E:/PHANI/Interview/tmp/c05_role_review_probe.py.

Correction: before changing a password or granting privileges, verify an existing role is a safe intended runtime identity, including effective attributes, memberships/SET ROLE access, ownership and relevant grants. Reject unsafe or ambiguous existing identities rather than silently demoting an operator or claiming that refresh made it restricted. Retain safe idempotent refresh for a verified runtime role. New-role tests alone are insufficient.

Acceptance: safe fresh-cluster tests for privileged existing roles, direct CREATE, membership/ownership as relevant, rejection without unintended password/permission changes, a safe existing-runtime refresh and the full runtime thin path. Keep the table grant map and audit protections.

## R20 [P2]: bound the HTTP method metric dimension
