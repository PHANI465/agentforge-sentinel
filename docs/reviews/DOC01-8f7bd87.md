## Why R58 and R59 close

- Recovery now asks the kernel whether a POSIX process group exists **after**
  scanning `/proc`. A group member forked after the PID snapshot is therefore
  still detected. A live, zombie-only, inaccessible or reused group keeps the
  record; only `ESRCH` allows cleanup. The group-existence query sends signal
  0 and cannot kill a process. Earlier unreadable-member and leader-identity
  guards remain.
- An independent native probe recreated the original fork-after-list order
  with a real session leader, member and descendant. It now returned
  `group_members_alive_kept`, retained the record and left the verified
  descendant alive for the probe's exact-PID cleanup. The original unreadable
  member probe returned `group_state_unknown_kept`.
- The independent nonzero-child probe still returns `status: error` and
  `invalid_child_output:exit_7` for a purported `complete` document. The
  validator's required-field and genuine-worker controls pass.

## Follow-up before API exposure

The existing Windows `test_crashed_supervisor_is_recoverable` failed in one
independent focused run, matching intermittent author failures. The author
reports passing final full runs, and the independent full worker run passed.
The exact cause of that intermittent failure is not proven. A controlled

an error and leave an orphan `r_*.tmp` recovery file, while confirming the
child stopped and removing its owned run directory. The same `.tmp` shape was
left by the failed focused test, which supports—but does not prove—the
replacement-race explanation. This is a **nonblocking Part A reliability
follow-up** because the worker is local and no parser process was left alive;
resolve it and add a regression before exposing the worker behind an API.
