## Remaining R15 [P2]: a delayed refresh can overwrite the current filter

Location: [Workbench.tsx:139](E:/PHANI/sentinel-wt/cursor-analyst-ui/web/src/ui/Workbench.tsx:139), specifically refresh's await loadOverview followed by loadQueue at lines 141-142.

refresh captures stateFilter and cursor history from its render, then awaits loadOverview before dispatching the queue request. While that await is pending, the user can change the filter and receive correct results. When the older refresh resumes, it starts a request using its captured old query. loadQueue gives that request a newer generation, so the stale query wins despite the selector retaining the user's newer filter.

Independent exact-source React/JSDOM reproduction:
1. Select a seeded awaiting-approval case and approve it.
2. Delay the overview request made by the ensuing refresh.
3. Change the queue filter to Closed; closed-only rows appear.
4. Complete the delayed overview request.
5. The old refresh requests the all-state queue, replaces the rows and leaves the selector on Closed.

Observed query order: all -> closed -> all. Before completion: filter=closed, closed-only row visible, all-state row absent. After completion: filter=closed, closed-only row absent, all-state row visible. Probe: E:/PHANI/Interview/tmp/u01_r15_refresh_probe.cjs, exit 0, using existing source/dependencies without checkout changes, network or model calls.

Correction: tie refresh dispatch to the current queue query/intent, not only request start order. Read the latest authoritative filter/cursor context at dispatch, or fence/discard refresh work whose initiating query is no longer current. Keep filter and pagination state consistent together; do not silently reset the user's query. Apply the invariant to mutation and ingest refresh paths, including work awaiting overview. Add the concrete deferred mutation-refresh regression and retain the direct reversed-response and duplicate-Next tests.
