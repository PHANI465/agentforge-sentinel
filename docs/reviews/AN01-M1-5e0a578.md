## R56 — P1: interruption after a rollback reply bypasses final close

References: scripts/report_benchmark_support.py:960 bounded_call interrupt handler;
:1206 _run_admitted finally;:1233 _rollback.

The new interrupt handler retires only while done.is_set() is false. If ROLLBACK has
answered and Ctrl-C/SystemExit occurs as its waiter returns, no retirement occurs.
The exception exits _rollback while it is itself inside _run_admitted's finally, skipping
the later close_normal() call. end_coordinator runs, but connection finalization does not.

The independent probe uses a synthetic connection and real run_statements/bounded_call.
It lets the real wait helper finish, then injects the interrupt at the third wait (Ka,
one read, ROLLBACK). Both exception variants propagate as required, but leave:
**close_calls=0, closed=false, resources=(0,1), quarantine=0**. The healthy control closes
once and reaches(0,0). There is no running SQL user at the interruption, so this is not a
legitimate busy-lease transfer. Native and Windows results match.

Ensure connection finalization executes even when rollback/finalization itself raises,
including a post-reply interruption. Preserve KeyboardInterrupt/SystemExit and the
original error, close only when safe, and otherwise retain an actual reachable owner/lease.
Do not release a reservation without confirmed close or close under a live SQL thread.
Cover healthy, busy, already-answered and failed-close paths; keep workflow quarantine untouched.
