## R50 — High: local-day coverage does not cover the public UTC window

Location: `AN01-decisions-r3.md:57`, the zone-table range and checker `starts()`.

The proposal equates local dates2000-01-01 through2038-01-01 with the UTC request range
`[2000-01-01T00:00Z, 2038-01-01T00:00Z)`. Independent boundary probes show:

- UTC2000-01-01T00:00 is **1999-12-31 in New York**, before the first pinned local date.
  Its valid first report bucket needs the December31 local midnight and next boundary.
- Just before the upper UTC limit is **2038-01-01 in Kolkata/Tokyo**. Its full day length
  needs the **2038-01-02** midnight, beyond the last date actually derived. The checker
  silently extends the final offset past the declared range instead of proving it.

Pad the derivation for all containing local dates and next-midnight sentinels required
by valid UTC requests, or explicitly propose a different public domain. Keep request
validity separate from lookup-table padding; never clamp or guess outside pinned coverage.
State validation after local-date conversion. Add lower/upper-bound known answers in
every zone and check the entire valid start domain rather than claiming coverage from
a truncated sample. No production report runtime exists yet; this is a design/checker gap.

## R52 — Medium: the inherited budget does not cover connection waits as claimed

Locations: decision §5.1 and phase C; existing `agents/budget.py:357,377`.

`open_connection` calls `psycopg.connect` synchronously; `bounded_call` only wraps later
operations on an already-open connection. Reusing BoundedTransaction therefore does not
by itself impose an absolute monotonic deadline on connection acquisition. Independent
fault injection (no network/database) gives a2100 ms deadline and requested2-second
connect_timeout; a stalled connector returns after2344 ms and is returned after the
deadline. This demonstrates the caller's control flow, not real-driver timing behavior.

The planned50/100/250 ms cancellation cases are also ambiguous: using those as the
pre-connect total budget refuses **before connection** in all three cases (0 connect
calls), because the helper requires at least2 s for a connection. A50 ms statement cap
is below MIN_DB_MS100 as well. Such a refusal cannot be reported as a submitted query's
cancel/quarantine result.

Prefer an explicit separate connection policy and a shared monotonic report budget
starting after acquisition, or separately design/prove bounded connection acquisition
and its late-operation capacity. Do not promise the latter merely by importing the SQL
wrapper. Specify report-specific phase/reserve (do not inherit the workflow's5-second
terminal reserve), timeout meanings, finite quarantine admission and cleanup ownership.
Separate pre-submission refusal controls from submitted-query/lock/withheld-reply controls
with feasible budgets and explicit submission proof. None requires production edits now.
