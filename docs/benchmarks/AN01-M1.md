Audience: Codex, reviewing the controller and resource evidence before any full-size
measurement assignment.

## 3. Budget and lease adapter

- **Admission before connecting.** Admission checks `active < M` and `reserved < Q` under one
  lock and takes both slots before any connection attempt.
- **When the reservation is released.** Exactly once: on a connect failure without a
  connection, or at the actual close.
- **Retirement.** It keeps the reservation: the lease's final close owns it. The report
  quarantine is separate from the workflow `QUARANTINE`; a test checks that the workflow
  count is unchanged throughout.
- **Report budget `B`.** It starts after the connection is acquired. The connection is outside
  `B` and is timed separately. Before every SQL statement, Ka arms the server timeouts with
  `floor(work_end − now) − REPLY_MARGIN_MS`. Below 100 ms the statement is not sent.
- **Waits.** Each reply is awaited until `work_end`. ROLLBACK is awaited until `B`.

Proved by the following tests.

**With controlled fakes:**
- a healthy close releases once;
- an answered error rolls back, then closes once;
- no reply: the connection is retired and the reservation held. A late return then closes it
  once. The request's own close attempt is a no-op, so there is no double close;
- a delayed final close keeps the reservation held;
- the R52 interleaving: one retired lease plus two concurrent requests gives exactly one
  admission and one `admission_refused`, so reservations never exceed Q;
- the `M` limit refuses before any connect attempt;
- 16 threads churning admissions never exceed M or Q;
- a connect failure releases the reservation;
- a workflow quarantine entry does not affect report admission;
- the refusal boundary: B = 300 and 349 are refused, 400 is not.

**Real PostgreSQL controls,** proved in the tests and in each S6 run:
- **C1:** refused before submission. The statement counter is 0 and the owner observer sees no
  tag.
- **C2:** `pg_sleep(5)` is cancelled by the server with 57014 inside the work phase. The
  observer sees it active.
- **C3:** an `ACCESS EXCLUSIVE` holder blocks the statement. The observer sees it waiting on
  `Lock`. The statement timeout fired before the lock timeout every time (57014).
- **C4:** the owned relay sees the tagged statement and withholds its reply. The connection is
  retired, then reaches its final close and drains.
- **C5:** a test gate holds two retired leases' final closes, so Q is 2/2 reserved. The third
  request is refused with 0 connect calls. Releasing the gate closes each lease once and
  drains to 0. A fresh request then succeeds. This is fault injection, not cancellation
  latency.

**Prototype deviation (finding R-M1-1).**
- **The race.** Under the literal r3.2 arming rule (`floor(work_end − now)`), the server timeout
  fires about one round trip *after* the client stops waiting, so a server cancellation could
  never be observed as answered.
- **What the prototype does.** It arms 30 ms early (`REPLY_MARGIN_MS`, provisional).
- **That margin is not always enough.** In one of the five native C2 runs at B = 1,250, the
  reply did not arrive within it; see §5. The design needs a decision: the margin size, or
  letting statement replies wait into part of `R`.

**Clock (finding R-M1-2).**
- **The problem.** `time.monotonic()` on Windows is `GetTickCount64` with a resolution of
  15.625 ms, and the first smoke recorded quantized medians (15/16/31/47 ms).
- **The fix.** The prototype's report clock is `perf_counter` (QueryPerformanceCounter, 100 ns).
- **Not fixed.** Accepted `budget.py` has the same Windows coarseness; it is noted only.

There are seven platform stages and three offline steps.

**The rules are pure functions, unit-tested:**
- rule 1: joint across both platforms, and it never picks an unmeasured variant;
- rule 2: N\* is monotone over sizes, with the guard checks;
- rule 3: control triggers;
- rule 4: spills;
- rule 5: a matched comparison with no causal share assigned to JSON;
- rule 6: missing evidence means "not demonstrated";
- rule 7: the label.

**Supervisor.**
- **Constants:** 2300 / 2350 / 300 / 2650 / 2700 s, pinned by a test, with a 900 s setup
  deadline. Tests and smokes use explicitly labelled *smaller* budgets: tiny is 240/270/60/330/340
  and the stall tests use 12/15/30/45/50.
- **How it supervises.** The controller is the stage command. It records a pending launch
  before starting the worker, then the worker's identity. The work/wait deadline is enforced
  from outside the worker.
- **What it stops.** Only a worker whose identity still matches, and only clusters that
  `database_state` verifies as this run's. Stops have bounded waits, and success is reported
  only after the process is confirmed gone.
- **When cleanup is unconfirmed:** exit 4, the recovery record and the run lock are kept, and
  every later stage is refused until `recover` confirms.
- **Checkpoint.** It records statement, setup, zone and source digests, and a changed digest
  refuses the stage. Each stage runs once, a started cell is never re-run, and unstarted cells
  are listed as not run.
- **Public records.** They are allow-listed, and writing one refuses any DSN, home or run
  path, user name, "password", "token" or traceback.

**Tests with real supervised processes** (real cluster and worker processes):
- a setup stalled after migration is stopped at the deadline, with worker and cluster
  confirmed stopped;
- an injected refusal to stop leaves the run blocked; the next stage is refused, and `recover`
  then stops the verified worker and cluster;
- after a real S1, S2's connector never returns; at the deadline that cell is
  "interrupted (outcome unknown)" and the rest are "not run".

**Preflight (finding R-M1-3).** The tiny S1 measured average row sizes of 936 B per
transaction and 1,087 B per outcome. From that, the planning estimate is 2,600 B per row.

| Full-size stage | Cluster-data estimate |
| --- | --- |
| S1–S2 | 3.6 GB |
| S4–S6 | 5.1 GB (D1 + D2) |
| S8 | 8.7 GB (with the shadow copy) |

- **Effect.** The full grid's own preflight therefore **refuses S4 onward** against the
  design's 4 GB bound (pinned by a test). This needs a design decision before any full-size
  assignment. Nothing was changed to make space.
- **WSL.** Preflight also checks the host drive that backs the WSL disk. On the smoke host,

## 5a. Gate failures after the smoke, and the measurement correction

Two Windows gate runs at `cd3517d` did not certify. Their evidence is in `.agent/gate-failed-1/`
and `.agent/gate-failed-2/`.

1. **My own invocation error.** `PYTEST_ADDOPTS` was given a backslashed JUnit path. Pytest
   stripped the backslashes, so the XML landed as an untracked file in the worktree root.
   `agent_check` then correctly refused to certify a changed tree.
   - All six checks still passed: 875 passed and the one allowed skip.
   - That run's own XML validates.
   - Rerun with a forward-slash path.
2. **One real failure under full-suite load:** `test_c2_submitted_and_cancelled_by_the_server[400]`.
   - The server *did* answer with 57014. The waiting thread noticed it at 151.27 ms, against a
     work end of 150 ms.
   - The waiter polls at most every 5 ms, and Windows sleep can overshoot. So the noticed time
     is not the arrival time, and whether the reply arrived before or after the work end is
     unknown.
   - **Correction 1, measurement.** The SQL thread now records when the reply arrives
     (`error_at_ms`). The noticed time is kept separately (`error_noticed_ms`), and
     deadline-to-error latency uses arrival. The `f00df8c` smoke latencies above used the
     noticed time.
   - **Correction 2, the tests. Reviewer attention: assertions changed after a gate failure.**
     The C2 and C3 gate tests had asserted the R-M1-1 race outcome as if it were deterministic.
     They now assert the mechanism under either design outcome:
     - submission is proved by the observer;
     - *answered*: the expected SQLSTATE, ROLLBACK answered, one normal close, not quarantined,
       arrival no later than notice;
     - *no reply*: retired, then drained to zero with one final close.
   - **Strictness kept elsewhere.** The benchmark's phase C cells are still strict: a server
     answer that misses the margin fails the cell, as native C2:1250 did.

### What changed

| Finding | Correction |

| **R53** recovery vs a live controller | **The run slot.** Every `stage`, `recover` and `cleanup` invocation holds an exclusive OS advisory lock on `run.slot` (`msvcrt.locking` on Windows, `flock` on Linux) for its whole lifetime. The OS releases it when the process exits, however it exits. Holding it therefore proves that no controller or recovery is running in any process, and that includes the interval after the run lock is taken and before a worker is recorded. It is never stolen, and the worker never inherits it.<br><br>**The run lock.** It names its invocation: pid, creation time, executable (the accepted `local_stack` identity) and a fresh token. It is written before any mutable stage work, and only the invocation with that token removes it.<br><br>**Recovery** acts only when the lock's invocation is provably absent:<br>- its process is gone, or its pid is reused;<br>- or it recorded a hand-off. A controller whose cleanup is unconfirmed rewrites the lock as `handoff: recovery`, under its own token, which must match `blocked.lock_token`.<br><br>An incomplete identity refuses, and so does an unreadable or uninspectable one; this includes `93583a`-format locks, which must be inspected and removed manually. A reused pid is never signalled. Recovery then stops only a verified owned worker and verified owned clusters, and removes only the lock it inspected.<br><br>**Interruption.** A controller that fails or is interrupted after taking the lock releases it only if no worker was ever recorded. Otherwise it hands the lock to recovery. |
| **R54** evidence and selections | **Typed, bound records.** Stage records are now `schema` 2. `select` and `report` refuse a set that cannot be combined:<br>- another schema or profile;<br>- statement, setup, zone or source identities that differ from the running code (old `f00df8c`/`93583a` records cannot be combined with new code);<br>- a platform contradicted by its environment;<br>- the same record twice;<br>- two records of one stage and platform (a later record can never replace a first result);<br>- a cell outside its stage.<br><br>**Cell checks.** A complete cell is checked for its registered outcome count and finite times, medians and maxima, and for its EXPLAIN evidence. An unknown required metric means not demonstrated. `rollback_ms` is measured from sending ROLLBACK to the arrival of its reply.<br><br>**Selections.** A selection carries its binding: profile, identities digest, platform pair and the per-record sha256 values, plus its own digest. | **R55** budget and late replies | **Recheck.** After Ka answers, the budget is rechecked immediately before the report SQL. The armed value is always at least 100 and never zero (no-limit).<br><br>**Waits.** `bounded_call` raises `BudgetExpired` for a non-positive or NaN wait before any thread starts.<br><br>**Late replies.** A reply whose recorded arrival is after the wait deadline is `late_reply` (503). ### Timing policy (R-M1-1 decision applied)

- **Unchanged:** `B`, `R`, `work_end` and the 30 ms margin. No reserve is borrowed.
- **Strict benchmark cells.** C2/C3 are proved only if:
  - the observer saw the statement;
  - the outcome is the expected server answer;
  - its arrival was no later than `work_end`;
